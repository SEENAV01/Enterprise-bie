# Batch005: evaluation and release integration

## What this package is

The cumulative, local Section17 source covers all50 original task IDs. It is not a complete native Enterprise-bie application, not a claim that all original capabilities are fully closed, and not permission to bypass section-level audit. The frozen Batch004 baseline passed962 tests before changes. New behavior is additive: no inherited executable code, test or tool was edited.

The new runtime is in `bie/evaluation/benchmarks/release/` plus `metrics/regression.py`. Existing callers retain the16-metric historical `metrics.evaluate` API. New callers use `release.deterministic.evaluate_metric` for17 metrics; `release.deterministic.execute` adds full assessment bindings and a service-code pin. Do not silently expand historical benchmark rosters or rewrite historical test expectations.

## Operator-owned versus candidate-owned inputs

Candidates supply answers/artifacts, never their own authoritative scores, private rubrics, policy thresholds, review identities or signature keys. The operator supplies the pinned reference, rubric, release manifest, evaluator roster and policy. Assessments are generated by the protected evaluator service. `assessment_sha256` is a content digest, not a signature. The low-level aggregation and CLI interfaces intentionally accept operator-generated assessments; exposing these directly to candidate workers would violate the threat model.

A context binds `run_id`, `case_id`, `domain`, `metric_id`, `candidate_sha256`, `reference_sha256`, `rubric_sha256`, `dataset_sha256`, `environment_sha256` and `split`. Pins must come from independently controlled evaluator state. Recomputing a pin from an untrusted caller's changed reference is not authentication.

## Run the local diagnostics

From `combined_source/`, use a fresh output directory:

```bash
python -B tools/run_section17_batch005_tests.py --output-dir /tmp/bie-tests-new
python -B tools/run_section17_batch005_diagnostics.py --output-dir /tmp/bie-diagnostics-new
```

The diagnostic driver executes17 deterministic metric profiles;17 model-adapter calls return explicitly authored fixture responses;17 human-review assessments use a clearly marked test key and fixture trust metadata. It then persists seven declared scenarios, including one DIAGNOSTIC_PASS and six BLOCKED results, verifies stored receipts after reopening SQLite, and checks duplicate-attempt rejection. This proves local contract execution, not model-judge accuracy, real human review or native BIE quality.

## Operator CLI

```bash
python -B -m bie.evaluation.benchmarks.release \
  --manifest MANIFEST_INPUT.json --policy POLICY.json --assessments ASSESSMENTS.json \
  --manifest-sha256 <trusted-manifest-digest> --policy-sha256 <trusted-policy-digest> \
  --database /private/eval/release.sqlite3 \
  --campaign-id governed-campaign --attempt-id unique-attempt \
  --output-dir /private/eval/new-result
```

Optional `--attestations`, `--artifact-evidence` and `--trust-metadata` supply operator-controlled external evidence. Trust metadata contains `secret_env`, not a raw secret. Only explicitly named `BIE_ATTEST_*` environment variables are read; their values are base64-encoded keys of at least32 bytes. No production key ships in this package. Fixture keys are refused in production mode. Exit0 can mean DIAGNOSTIC_PASS, which is visibly not production acceptance; BLOCKED uses exit2.

## Release semantics

The production benchmark gate requires all17 metric IDs, mandatory core floors, full measured coverage, HOLDOUT/independently reviewed reference metadata and authenticated evidence for policy approval, golden-reference review, independent evaluation, native-book E2E, video-render QA, game-runtime QA and security/rights review. Signatures bind the exact manifest, policy and assessment set. Evidence bytes must match the attested digest. Expired/revoked/unknown/wrong-scope or fixture-key attestations fail closed. The configured authority is responsible for the truth of the signed external claim; verifying a signature alone cannot inspect an unseen native run.

Even a valid production benchmark decision sets `release_authorized=false` and `product_accepted=false`. Deployment authorization and whole-product acceptance are separate approvals. The provided diagnostics have no real production attestations and cannot legitimately satisfy native/golden acceptance.

Cohen kappa is `null`/UNDEFINED for degenerate panels. A policy demanding defined kappa blocks in that case; a policy using observed agreement and score differences can explicitly leave `minimum_kappa=null`. This is not a universal statistical-quality guarantee. Numerical policies in examples are authored development settings, not empirically calibrated enterprise thresholds.

## Storage, audit and reproducibility

Release campaigns freeze reference/roster/environment/policy metadata while allowing genuinely changed candidate/artifact attempts. Reusing the same artifact in a campaign is blocked, including after failure. A new campaign must be a governed decision; campaign names alone do not prevent an unauthorized operator from cherry-picking campaigns. Attempt receipts bind external evidence inputs and public trust metadata without recording secrets. RUNNING or corrupt receipts are not accepted as successful results.

The SQLite ledger is single-host, operator-controlled storage. Hashes and SQL uniqueness are not off-host authentication or a multi-tenant boundary. File symlink guards are not a race-proof sandbox. Production filesystem/process isolation, durable signed anchoring, crash-recovery policies and canonical migration review remain open.

`tools/build_section17_archive.py` creates deterministic ZIP entries with fixed timestamps and a complete SHA256 manifest. It refuses symlinks and existing output paths. `tools/verify_section17_package.py` verifies manifests and safely extracts archives. Archive determinism is distinct from reproducible native compilation/rendering.
