# REPAIR004–007 — domain repair contract and safety boundary

## Pipeline
Actual immutable defect report + exact bound request/policy + owner authorization
→ deterministic domain transform → full inherited domain evaluator → unsigned witness
and proposed bytes → NEW proposal approval → inherited bounded staged execution
→ fresh domain/downstream/preservation validation → STAGED_FOR_REVIEW or rejection.

Neither the candidate nor source text can select an executable, owner, policy,
validator, signature key or resource budget. The request must be listed in the
snapshot, every source/output artifact must belong to that same snapshot, and the
classified report must match its current request AND domain-policy digest. Reports
for other artifacts cannot justify this request's repair. Rejections cannot be
outvoted; missing and test-only authorizations cannot become operational approval.

## Mutation boundaries
REPAIR004 changes only derived block text/hash and existing citation positions/digests.
REPAIR005 changes existing deductive step support and step order, not root knowledge.
REPAIR006 changes approved route order and response-event timing/gating, lengthening
existing segments only within explicit budgets. No route or rubric is deleted.
REPAIR007 changes beat/scene timing only. Existing words, source conditions, claims,
meaning, voice and route membership remain unchanged.

The algorithms escalate rather than select an unreviewed interpretation. Full domain
reports may remain BLOCKED without renewed semantic reviews even when the specific
repair-area checks pass. Those blockers are included in the generation witness.
Downstream check closure is computed by unchanged repair_v2; no worker selects its
own subset or copies former PASS evidence to new bytes.

## Assurance and reproducibility
Same byte snapshot, policies, limits and evaluation time yield identical proposed
bytes and witnesses. Evaluation time is supplied explicitly by the operator; fixture
clocks do not prove production freshness. Source artifacts are reread after generation.
Original inputs are never edited in place. Content-addressed proposal files use exclusive
creation and no-follow checks in private operator-owned directories. This is not
protection against a privileged attacker or a hostile-code execution sandbox.

The CLI is unauthorized read-only preview. Use the authenticated API and existing
staging controller for effects. Secrets and reviewer services are provisioned externally.
Three JSON schemas are structural aids; strict Python contracts implement cross-field
scope, role, byte, ownership and semantic checks. Existing domain contracts are reused.
