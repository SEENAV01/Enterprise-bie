# M132 — Security, Identity, Access Control & Secret Boundary Layer

M132 establishes the security boundary across BIE users, services, artifacts, workflows, datasets, events and secrets.

## Core separation

The architecture keeps these concepts distinct:

```text
Identity
   ≠
Permission
   ≠
Secret
```

Authentication establishes who is acting.

Authorization determines what that principal may do.

Secret references identify credentials without embedding secret values in policies or artifacts.

## Principals

A principal can represent a user or service.

Service identities are first-class principals and can carry explicit scopes.

## Authentication context

An authorization request can require an authentication context containing:
- principal ID
- authentication method
- session ID
- claims

Unauthenticated requests are denied.

## Resource scopes

Resources have explicit scopes.

Example:

```text
workspace:course-17
project:physics
artifact:lesson-1
```

Authorization can therefore be scoped rather than globally granted.

## Authorization

Policies can define:
- resource type
- action
- allowed roles
- required scope
- effect

The reference implementation follows deny-by-default semantics.

## Least privilege

A principal should receive only the permissions required for its task.

Service identities should therefore have narrowly defined scopes instead of broad platform-wide access.

## Capabilities

Capabilities provide a more explicit action/resource check:

```text
Capability
   ↓
Resource Type
   +
Action
   +
Scope
```

This can be used for sensitive operations where role membership alone is too broad.

## Secrets

BIE policies and artifacts should store secret references, not secret values.

```text
Artifact
   ↓
secret_ref
   ↓
Secret Store
```

The reference implementation supports provider + secret ID + optional version.

## Privileged actions

Sensitive actions can require:
- specific role
- explicit justification

This creates a boundary around operations such as production publishing, credential rotation or destructive administration.

## Relationship

M131 governs artifact lifecycle.

M132 governs who or what may access and mutate those artifacts.

M128/M129 provide event infrastructure and contracts.

M116 audit should record security decisions and privileged actions without exposing secret values.

## Important boundary

The reference implementation is an authorization model, not a complete production identity provider or cryptographic implementation. Production deployment requires a trusted authentication system, secure secret manager, key rotation, token validation, encryption and infrastructure-level controls.
