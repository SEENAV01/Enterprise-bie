# M102 — Asset / Artifact Registry & Dependency Graph Layer

M102 turns generated outputs into a connected, versioned asset system.

## Registry

Every asset can have:
- stable asset ID
- type
- version
- content hash
- status
- metadata
- tags

This allows a book/course to reference assets without treating generated files as anonymous blobs.

## Dependency graph

Dependencies are explicit edges.

Examples:

`concept → scene`

`equation → diagram`

`diagram → animation`

`animation → narration timing`

`scene → lesson video`

The graph can therefore represent the complete production dependency structure.

## Invalidation

When an upstream asset changes, M102 propagates invalidation through downstream dependencies.

Example:

`equation changes`

can invalidate:

`diagram → animation → narration timing → final video`

Only affected outputs need rebuilding.

## Rebuild planning

The rebuild planner computes a dependency-aware order.

Dependencies are rebuilt before their dependents.

Cycles are rejected rather than silently producing an ambiguous build order.

## Versioning

Asset versions are separate from the asset identity.

This supports:
- rollback
- historical references
- reproducibility
- A/B variants
- controlled updates

## Caching

Cache keys can incorporate:
- asset type
- input references
- versions
- production parameters

Thus identical production requests can reuse previously produced artifacts when policy allows.

## Course-scale implication

A complete course can now be represented as a graph rather than a sequence of independent files.

This is important for:
- incremental builds
- parallel production
- partial regeneration
- change impact analysis
- cost reduction
