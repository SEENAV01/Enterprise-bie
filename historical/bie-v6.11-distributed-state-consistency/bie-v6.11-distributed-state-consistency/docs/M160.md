# M160 — Distributed Data & State Consistency Layer

M160 defines contracts for safely maintaining state when multiple workers or services can read and update the same logical entity.

## Versioned entities

Every mutable entity can carry a monotonically increasing version.

```text
Entity v7
  ↓
Update expecting v7
  ↓
Entity v8
```

## Optimistic concurrency

A write includes the version it observed.

If the stored version differs, the write is rejected as a conflict rather than silently overwriting newer state.

```text
Stored = v8

Client A expects v8 → ACCEPT → v9
Client B expects v8 → CONFLICT
```

## Sequence numbers

Sequence numbers provide ordered state/event positions for a resource.

An operation is accepted only when its sequence matches the expected next position.

## Version vectors

Version vectors provide a foundation for reasoning about distributed causality.

Two vectors can:
- dominate another vector
- or be concurrent

Concurrent versions require conflict handling rather than assuming a global ordering.

## Transactions

Transaction contracts group operations under an explicit transaction identity and isolation level.

The reference layer models commit/abort states but does not implement a database transaction engine.

## Idempotent state transitions

State transitions can carry an operation ID. Repeating the same operation ID returns `ALREADY_APPLIED` rather than applying the transition twice.

## Consistency contracts

Supported conceptual consistency levels:

```text
EVENTUAL
CAUSAL
STRONG
```

Optional guarantees can include read-your-writes and monotonic reads.

## Conflict handling

Conflicts preserve both competing versions/states and can later be resolved with an explicit strategy.

The reference helper demonstrates a resolution strategy field; production systems should select strategies according to domain semantics rather than blindly using last-writer-wins.

## Reconciliation

Reconciliation models convergence between source and target state.

```text
Diverged
   ↓
Reconciliation
   ↓
RUNNING
   ↓
CONVERGED / FAILED
```

## Relationship

```text
M159 Eventing
      ↓

      ↓

      ↓

```

M158 leases/fencing protect ownership during distributed work.

M159 delivery semantics provide the asynchronous transport.

M151 reliability can observe conflicts and reconciliation failures.

M156 recovery can restore state and then trigger reconciliation.

## Important boundary

The reference implementation does not implement a distributed database, consensus protocol, CRDT library, serializable transaction engine, global clock or automatic domain-specific conflict resolver.
