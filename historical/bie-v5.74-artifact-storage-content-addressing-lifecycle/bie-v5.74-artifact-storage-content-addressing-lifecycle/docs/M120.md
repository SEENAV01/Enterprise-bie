# M120 — Artifact Storage, Content Addressing & Lifecycle Layer

M120 defines the canonical storage and lifecycle contract for generated artifacts.

## Content addressing

Artifact identity can be derived from a cryptographic content hash:

```text
bytes
  ↓
SHA-256
  ↓
artifact_id
```

The same bytes therefore map to the same identity.

This enables deduplication and cache-friendly storage.

## Immutability

An artifact identity refers to concrete content.

A changed artifact should receive a new identity rather than silently replacing the existing bytes.

Metadata may be associated with the artifact record, while the content identity remains content-addressed.

## Lifecycle

Reference states:

```text
STAGED
  ↓
VALIDATED
  ↓
PROMOTED
  ↓
RELEASED
  ↓
ARCHIVED
  ↓
GC_ELIGIBLE
  ↓
DELETED
```

Invalid state jumps are rejected.

## Promotion

Promotion from VALIDATED to PROMOTED requires a validation reference.

This connects M115 quality verification to artifact lifecycle state.

## Retention

Retention policy can specify:
- whether released artifacts are retained
- retention duration
- whether references protect artifacts

The policy is deliberately separate from storage implementation.

## Garbage collection

Garbage collection should be planned, not performed blindly.

Referenced artifacts are protected when the policy requires it.

Only archived or explicitly GC-eligible artifacts become deletion candidates.

## Lineage

Artifact records can carry parent references.

This allows the storage layer to participate in the provenance chain established by M113 and M116.

## Relationship

M113 tracks asset dependencies.

M114 identifies reproducible builds.

M115 validates artifacts.

M119 controls secure generation.

M120 stores and transitions the resulting artifacts safely.

## Important boundary

This is a logical storage contract.

A production deployment still needs durable storage, access control, backups, encryption and disaster recovery mechanisms appropriate to the environment.
