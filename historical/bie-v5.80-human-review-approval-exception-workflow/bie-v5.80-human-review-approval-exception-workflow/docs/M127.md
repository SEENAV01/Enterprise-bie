# M127 — Human Review, Approval & Exception Workflow

M127 introduces controlled human intervention when automated evaluation cannot safely make the final decision.

## Review lifecycle

```text
QUEUED
  ↓
IN_REVIEW
  ├── APPROVED
  ├── REJECTED
  ├── ESCALATED
  └── OVERRIDDEN
          ↓
       CLOSED
```

Invalid state transitions are rejected.

## Reviewer authorization

Review cases can require a specific reviewer role.

A reviewer must be active and possess the required role before performing the protected action.

## Structured annotations

Reviewers can attach annotations with:
- category
- severity
- comment
- optional location

This makes feedback machine-readable and useful for downstream rework.

## Approval and rejection

A decision records:
- review ID
- reviewer ID
- decision
- rationale
- artifact ID

A rationale is required.

## Escalation

Critical or blocking findings can be escalated to a designated role.

This prevents high-risk cases from being treated like ordinary reviews.

## Explicit override

An override records:
- original gate
- reason
- authority
- timestamp
- reviewer

An override is therefore an auditable exception, not a silent bypass.

## Dual control

For sensitive approvals, two distinct reviewers can be required.

The reference implementation supports two approvals from distinct reviewer identities.

Production policy can extend this with separation-of-duties rules.

## Relationship

M126 provides automated evaluation.

M127 handles cases requiring human judgment.

M115/M126 quality gates can be overridden only through explicit review policy.

M116 audit infrastructure should record these actions.

M120 artifact identity ensures the review attaches to a concrete immutable artifact.

## Important boundary

Human review does not automatically make an artifact safe.

The review policy must specify what reviewers are authorized to approve and which classes of findings require escalation or additional evidence.
