# M29 — Scene Planning + Storyboard Compiler

M29 transforms structured teaching-script units into atomic visual scenes.

## What M29 decides

For each scene:
- scene type
- teaching objective
- narration linkage
- evidence linkage
- visual elements
- animation events
- camera-event slot
- transition slot
- audio-sync anchor contract

## Atomicity

A scene should have one dominant explanatory job. Complex explanations can therefore become multiple scenes rather than forcing many ideas into one visual.

## Visual staging

Scene type determines a starting visual grammar:
- definition → term + definition + highlight
- diagram → diagram + labels + relationship emphasis
- process → system + sequential steps
- derivation → equation transformations
- worked example → problem → data → steps → answer
- question → question → response pause → explanation

These are planning primitives, not final rendered designs.

## Timing

Timing is explicitly audio-driven.

There is:
- no fixed scene duration
- no arbitrary maximum
- no requirement to make every scene the same length

Exact timing is populated after narration/audio analysis.

## Audio synchronization

The storyboard contains semantic sync anchors. Later audio analysis should convert them to exact timestamps/word/phoneme alignment.

## Remotion boundary

M29 targets the project's Remotion Scene DSL but does not yet generate final React/Remotion code. This separation lets the planner revise scenes without coupling pedagogical reasoning to rendering implementation.

## Important distinction

M28 = how the lesson is explained/narrated.

M29 = what each atomic visual scene must stage and animate.
