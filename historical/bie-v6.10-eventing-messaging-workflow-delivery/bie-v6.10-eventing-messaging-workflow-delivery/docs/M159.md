# M159 — Eventing, Messaging & Workflow Delivery Layer

M159 defines reliable asynchronous delivery contracts between BIE services and workflows.

## Events

Events identify:
- event ID
- event type
- payload reference
- producer
- timestamp
- tenant
- schema version

The payload can remain outside the event envelope.

## Topics

Topics provide publish-oriented routing with partitions and optional retention.

## Queues

Queues provide work-oriented delivery.

The reference contract supports bounded queue depth and explicit delivery semantics.

## Delivery semantics

Supported conceptual modes:

```text
AT_MOST_ONCE
AT_LEAST_ONCE
EFFECTIVELY_ONCE
```

The reference implementation does not provide a broker; semantics are contracts for an underlying messaging system.

## Idempotency

At-least-once delivery means consumers must tolerate redelivery.

An idempotency key can combine:

```text
operation + entity + request
```

Consumers can use this key to prevent duplicate side effects.

## Ordering

Ordering can be declared for a scope and keyed by an entity field.

Ordering guarantees depend on the production broker and partitioning strategy.

## Dead letters

Messages exceeding retry policy can be moved to a dead-letter state with the original queue, attempt count and failure reason.

## Replay

Replay plans specify a topic and position range and an optional target.

Replay is modeled separately from ordinary consumption so recovery/reprocessing is explicit.

## Backpressure

Backpressure policies can throttle producers/consumers when in-flight work or queue depth crosses a high watermark.

```text
Depth ≥ High Watermark
        ↓
     THROTTLE
        ↓
Depth ≤ Low Watermark
        ↓
     RESUME
```

## Workflow delivery

Workflow delivery contracts connect a workflow event type to a queue and declare whether idempotency is required.

## Relationship

```text
M158 Coordination
       ↓
M159 Event / Message
       ↓
Queue / Topic
       ↓
Delivery
       ↓
Worker
       ↓
Idempotent Side Effect
```

M150 provides telemetry/correlation context.

M151 reliability can observe delivery health.

M156 recovery can use replay and dead-letter handling.

## Important boundary

The reference implementation does not implement Kafka, RabbitMQ, NATS, SQS, Pub/Sub, a durable broker, exactly-once transactions or a production consumer runtime.
