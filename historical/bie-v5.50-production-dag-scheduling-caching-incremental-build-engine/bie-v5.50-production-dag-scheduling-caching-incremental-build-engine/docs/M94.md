# M94 — Production DAG, Scheduling, Caching & Incremental Build Engine

M94 turns the production graph into an executable build system.

## DAG execution

Assets are nodes.

Dependencies determine when a node becomes ready.

Independent nodes can execute in parallel.

This allows large lessons, books and courses to avoid unnecessary sequential production.

## Scheduling

The reference scheduler produces batches of ready nodes.

A production runtime can later replace this with:
- worker pools
- distributed execution
- GPU scheduling
- priority queues
- resource-aware scheduling
- remote workers

The architectural contract stays the same.

## Stable hashing

Build hashes can incorporate:
- node specification
- inputs
- production contract
- tool version

This creates a deterministic identity for a build result.

## Cache

If the same inputs and contract produce the same build hash, the artifact can be reused.

Caching is therefore based on content/build identity rather than a fragile filename convention.

## Incremental invalidation

When one node changes, only that node and its downstream dependents need invalidation.

Example:

`Scene 37 → Narration 37 → Final Composition`

If Scene 37 changes, unrelated scenes remain reusable.

## Resumability

A build can preserve completed nodes and cached artifacts.

If production stops halfway through a large course, the next run can continue instead of restarting from zero.

## Build manifest

A manifest records:
- build ID
- nodes
- artifacts
- tool versions
- source references

This becomes important for reproducibility and auditability.

## Scaling

M94 is designed for:
- one lesson
- full chapter
- complete book
- complete course
- large multi-asset projects

The same graph model scales by adding nodes rather than creating a different architecture.

## Important principle

M94 is an execution layer, not a content-generation layer.

It does not decide what should be taught or how it should be represented.

It executes the production contracts created upstream.
