# M200 — Storage, Persistence & State Backend Abstraction Layer

M200 defines vendor-neutral contracts for durable state and persistence backends.

## Key/value records

Records are identified by a namespace and key and carry a value, version and optional metadata.

## Blobs

Blobs reference content storage and can carry size, content type and checksum metadata. The abstraction does not dictate whether content is local, object storage or another backend.

## Collections and namespaces

Collections group records and can reference schemas and indexes. Namespaces provide isolation and metadata boundaries.

## Versioning

Version records provide optimistic concurrency information through version numbers and optional ETags/timestamps.

## Conditional operations

Supported reference conditions:

```text
EQ
NE
EXISTS
NOT_EXISTS
```

These conditions provide a portable basis for conditional writes and compare-and-set semantics.

## Transactions

M200 integrates with transaction contracts from M194 by allowing ordered storage operations inside a transaction.

## Snapshots

Snapshots identify a namespace state at a particular version.

## Consistency

Storage callers can declare:

```text
EVENTUAL
SESSION
BOUNDED
STRONG
```

The backend determines whether the requested semantics can be satisfied.

## Audit and observability

Storage events record persistence operations. Metrics expose latency and bytes read/written.

## Relationship

```text
M192 → Metadata / Schema
M193 → Query / Retrieval
M194 → Transactions
M195 → Distributed Coordination
M196 → Eventing / Messaging
M197 → Scheduling / Temporal Execution
M198 → Resource / Quota Management
M199 → Execution Runtime
M200 → Storage / Persistence / State
M150 → Audit / Observability
```

## Important boundary

M200 does not implement SQL, NoSQL, object storage, a filesystem, MVCC, replication, sharding or a particular database engine. It defines the portable state-backend contract.
