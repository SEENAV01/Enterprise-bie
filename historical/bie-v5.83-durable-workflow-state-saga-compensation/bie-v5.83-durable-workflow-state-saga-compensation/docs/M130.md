# M130 — Durable Workflow State & Saga / Compensation Layer

M130 makes long-running multi-step workflows recoverable across partial failure.

## Durable workflow state

A workflow has an explicit state machine:

```text
PENDING
  ↓
RUNNING
  ↓
SUCCEEDED / FAILED / WAITING / TIMED_OUT
```

Terminal handling can lead to:

```text
FAILED → COMPENSATING → COMPENSATED → COMPLETED
```

Invalid transitions are rejected.

## Checkpoints

A checkpoint can persist:
- workflow ID
- state
- completed steps
- workflow context
- sequence number

The latest checkpoint can be selected during recovery.

## Resume

If a workflow was interrupted while running or waiting and a valid checkpoint exists:

```text
Checkpoint
    ↓
Recover
    ↓
Resume from known state
```

This prevents unnecessary re-execution of already completed steps.

## Saga / compensation

Distributed workflows cannot always use a single ACID transaction across every external system.

Instead, completed actions can have compensating actions.

Example:

```text
Reserve Asset ✓
Create Render Job ✓
Publish Artifact ✗
        ↓
Compensate
        ↓
Undo Create Render Job
Undo Reserve Asset
```

Compensation is planned in reverse order of completed steps.

## Timeouts

Steps may define explicit timeout limits.

A timeout can result in compensation when a compensation action exists.

## Partial failure

The system explicitly distinguishes:

```text
all succeeded
vs.
partial failure
```

This is important for long-running workflows spanning multiple services.

## Relationship

M121 orchestrates distributed jobs.

M128 distributes lifecycle events.

M129 protects event contracts.

M130 provides durable workflow state and recovery semantics across those components.

## Important boundary

Compensation is not necessarily a perfect rollback. External side effects may be irreversible or only partially compensatable. Compensation policies must therefore be domain-specific and auditable.
