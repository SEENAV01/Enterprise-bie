# M67 — Asset & Visual Planning Engine

M67 converts pedagogical intent into a visual production specification.

## Purpose

A concept should not be visualized using one universal animation style.

M67 selects an appropriate visual modality based on:
- concept characteristics
- learning objective
- learner preference

## Supported modalities

The reference registry includes:
- static diagrams
- 2D/3D animation
- charts
- simulations
- process diagrams
- timelines
- equation builds
- tables
- visual metaphors
- maps
- code visualization

The registry is extensible.

## Reusable primitives

Visuals are assembled from reusable primitives such as:
- arrows
- labels
- axes
- vectors
- particles
- shapes
- equations
- charts
- diagram nodes/edges

This creates a visual vocabulary that can scale across an entire course.

## Visual specification

A visual spec contains:
- concept
- objective
- modality
- primitives
- animation plan
- narration synchronization cues
- source references
- render target

## Timing

Animation uses `CONTENT_DRIVEN` timing by default.

There is no artificial global video-duration constraint. Scene duration can be determined by explanation, narration and visual comprehension requirements.

## Source traceability

Visual specs retain source references so diagrams and representations can remain connected to their evidence.

## Renderability

Before rendering, the visual specification is checked for supported target and valid primitives.

## Continuity

Across a course, visual continuity can be checked using shared style tokens, identity references and coordinate-system requirements.

## Domain independence

M67 does not assume Physics.

A timeline may teach History, a process diagram may teach Biology, a chart may teach Economics, and code visualization may teach Programming.

## Relationship to M65/M66

M65 decides pedagogical strategy.

M66 observes learner interaction.

M67 decides how the selected teaching strategy should become visual language.
