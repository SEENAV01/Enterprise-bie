# M169 — Search, Indexing & Retrieval Layer

M169 provides a storage/search-engine-neutral contract for retrieval.

## Search query

A query can specify:
- index
- text
- filters
- facets
- sorting
- limit
- cursor

Limits are bounded to prevent unbounded retrieval.

## Index abstractions

Reference index types:

```text
INVERTED
COMPOSITE
VECTOR
KEYWORD
```

The contract does not implement a physical index.

## Filtering

Supported reference operators include:

```text
EQ NE GT GTE LT LTE IN PREFIX
```

Filters remain explicit and machine-readable.

## Ranking

Ranking profiles can select algorithms and field weights.

The reference package models BM25/SCORE/NONE profiles; actual ranking belongs to the search adapter.

## Faceting

Facets provide aggregate counts over a field and can define a limit and sort policy.

## Cursor pagination

Cursor pagination avoids relying solely on offset-based pagination.

```text
Page 1
 ↓
cursor
 ↓
Page 2
 ↓
cursor
 ↓
Page 3
```

The cursor contract is opaque to the domain layer.

## Retrieval consistency

Supported reference modes:

```text
EVENTUAL
SESSION
STRONG
```

The search adapter maps these to its actual guarantees.

## Reindexing

Index versions can migrate independently:

```text
Index v2
   ↓
Reindex
   ↓
Index v3
```

Progress is explicit so large indexes can be rebuilt without making the domain model depend on a particular engine.

## Query observability

Search events record:
- index
- query ID
- latency
- hits

This feeds M150 telemetry and can support query-performance analysis.

## Relationship

```text
M167 Persistence
      ↓
M169 Search / Retrieval
      ↓
M168 Cache
      ↓
M162 API
```

M164 policy can control search limits, scopes and feature rollout.

M166 privacy constraints and M163 tenant boundaries remain mandatory for protected/tenant data.

## Important boundary

The reference layer does not implement Elasticsearch, OpenSearch, Solr, a vector database, a physical inverted index, ranking execution or distributed search.
