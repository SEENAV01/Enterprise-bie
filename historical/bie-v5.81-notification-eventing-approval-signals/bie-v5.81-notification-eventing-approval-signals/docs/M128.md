# M128 — Notification, Eventing & Approval Signal Layer

M128 connects BIE subsystems through explicit domain events and reliable delivery semantics.

## Domain events

Every event has:
- unique event ID
- event type
- source
- timestamp
- correlation ID
- causation ID
- payload
- schema version

Example:

```text
REVIEW_APPROVED
     ↓
Event
     ↓
Event Bus
```

## Correlation

Correlation IDs connect events belonging to the same workflow/request.

Causation IDs connect an event to the event that directly caused it.

This gives a traceable event chain.

## Subscriptions

Consumers subscribe to explicit event types.

This avoids tightly coupling producers to individual downstream services.

## Idempotent delivery

Consumers use an event + consumer identity delivery key.

If the same event is delivered again, the consumer can detect it and avoid duplicate processing.

## Retry

Transient delivery failures can retry with exponential backoff and a maximum delay.

## Dead-letter

Events that exceed retry limits can be moved to a dead-letter state for investigation/replay.

## Notifications

Notification records track:
- event
- channel
- recipient
- template
- payload
- delivery state

This supports review and approval notifications without embedding notification logic into domain services.

## Approval signals

Review outcomes are explicit machine-detectable events:

```text
REVIEW_APPROVED
REVIEW_REJECTED
REVIEW_ESCALATED
OVERRIDE_CREATED
```

Downstream workflows can react without directly coupling to the review implementation.

## Relationship

M127 creates human review decisions.

M128 distributes those decisions and other lifecycle changes.

M121 can consume events to advance workflows.

M116 can consume events for audit/observability.

## Important boundary

The reference event store is an append-only in-memory model. Production deployment requires a durable event broker/store, retention policy, ordering strategy and operational controls.
