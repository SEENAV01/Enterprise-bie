# M121 — Distributed Job / Workflow Orchestration Layer

M121 turns individual production operations into reliable dependency-aware workflows.

## Why orchestration is needed

Large educational builds can contain:
- many lessons
- many scenes
- thousands of assets
- render jobs
- validation jobs
- repair/rebuild jobs

These operations should execute concurrently where dependencies permit.

## Workflow DAG

Jobs form a directed acyclic graph:

```text
Asset A ──┐
Asset B ──┼──→ Scene
Asset C ──┘      ↓
              Lesson
                ↓
              Course
```

A dependency cycle is invalid.

## Runnable jobs

A job becomes runnable only when all declared dependencies are complete.

This allows independent scenes/assets to run in parallel.

## Queue

Jobs can carry priority.

The reference queue orders pending work by priority.

A production implementation can extend this with:
- tenant quotas
- resource classes
- GPU requirements
- deadlines
- fairness

## Worker leases

A worker receives a lease for a job.

If the lease expires, orchestration can recover the job rather than assuming the worker is still alive.

## Retries

Retry behavior is policy-driven.

Reference transient failures include:
- timeout
- worker loss
- rate limiting
- temporary I/O

Permanent errors or exhausted attempts become terminal.

Exponential-style backoff prevents immediate retry storms.

## Idempotency

A job can derive an idempotency key from:
- job identity
- input content hash
- policy version

If the same logical job was already completed, the orchestrator can reuse the result rather than duplicate work.

## Checkpoints

A workflow checkpoint records:
- workflow ID
- completed jobs
- failed jobs
- workflow state

This allows a large build to resume after interruption.

## Partial rebuilds

Because dependencies are explicit, changing one input need not invalidate unrelated work.

Example:

```text
Scene 17 changed
      ↓
Rebuild Scene 17
      ↓
Rebuild dependent Lesson Render
      ↓
Leave unrelated scenes untouched
```

The exact invalidation policy belongs to the build system.

## Failure model

A job can be:
- pending
- running
- completed
- retryable failure
- terminal failure

This state model should integrate with M116 audit events.

## Relationship

M119 provides secure execution.

M120 manages artifacts.

M121 schedules the jobs that use those execution and artifact layers.

M115 provides validation gates that jobs can depend on.
