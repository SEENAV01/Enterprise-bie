# M100 — Governance, Provenance, Versioning & Reproducibility Layer

M100 answers the lineage question for every generated artifact:

**What exactly produced this?**

## Stable identities

Artifacts and builds receive deterministic identities derived from canonicalized manifests.

The identity is therefore tied to the declared production state.

## Version pins

The system can pin:
- source versions
- model versions
- tool/backend versions
- policy versions
- experiment versions

A build should not depend on floating versions if reproducibility is required.

## Provenance graph

Lineage is represented as nodes and edges.

Nodes can represent:
- source
- transformation
- model
- policy
- experiment
- artifact
- build

Edges express relationships such as:
- derived-from
- transformed-from
- generated-by
- rendered-by
- validated-by
- governed-by

## Build manifest

The manifest is the production receipt.

It records:
- artifacts
- source pins
- model pins
- tool pins
- policy pins
- experiment pins
- environment
- provenance

## Governance

Approvals are explicit records containing:
- target
- actor
- decision
- timestamp
- reason

This supports controlled release workflows.

## Reproducibility

The reference engine checks whether required production dimensions are present.

At minimum:
- sources
- models
- tools
- policies
- environment

A future implementation can extend this to:
- container/image digests
- dependency lockfiles
- hardware profiles
- random seeds
- dataset snapshots
- renderer settings
- compiler flags

## Manifest comparison

Two builds can be compared to determine exactly which declared production dimensions differ.

This supports:
- regression analysis
- release comparison
- debugging
- audit
- rollback
- reproducibility investigations

## Relationship

M99 recommends controlled policy changes.

M100 records exactly which policy and production state was actually used.

M100 therefore becomes the system's **chain of custody** for generated learning artifacts.
