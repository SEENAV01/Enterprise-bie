# M150 — Observability, Telemetry & Distributed Tracing Layer

M150 makes distributed BIE execution observable end-to-end.

## Trace

A trace represents one distributed operation and carries:
- trace ID
- root span ID
- operation
- service
- correlation ID
- workflow ID

## Spans

A span represents one operation within a trace.

Spans carry:
- span ID
- parent span ID
- service
- operation
- start/end
- status
- attributes

This creates a causal execution tree.

```text
Trace
 ├── API Span
 ├── Workflow Span
 │    ├── Task Span
 │    └── Worker Span
 └── External API Span
```

## Context propagation

Trace and correlation context can be passed from parent to child operations.

```text
Request
 ↓
trace_id
 ↓
workflow
 ↓
task
 ↓
worker
```

## Structured logs

Logs carry machine-readable fields plus trace/span/correlation identifiers.

Sensitive fields such as raw secrets and tokens should be redacted before persistence.

## Metrics

Metrics represent numeric observations such as:
- operation counts
- latency
- error rates
- resource usage
- cost

## Worker telemetry

Worker execution can record:
- task ID
- worker ID
- status
- start/end
- cost
- usage

This provides a foundation for BIE cost and performance analysis.

## Health signals

Services can emit health signals containing status, latency and error rate.

These signals complement M147 routing decisions.

## Diagnostic context

A shared diagnostic context ties trace, correlation, workflow and task identifiers together.

## Relationship

```text
M145 API
   ↓
M150 Trace
   ↓
M140 Workflow
   ↓
M144 Events
   ↓
M141 Worker
   ↓
M142 Artifact
```

M150 observes the execution chain without becoming the execution engine.

## Important boundary

The reference implementation defines telemetry contracts and local helpers. It does not implement a production telemetry collector, time-series database, tracing backend, sampling engine, alert manager or dashboard.
