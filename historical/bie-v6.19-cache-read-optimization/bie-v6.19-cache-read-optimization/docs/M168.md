# M168 — Cache, Materialization & Read-Optimization Layer

M168 introduces a storage-independent read-optimization abstraction.

## Cache keys

Keys are deterministic and can include:
- namespace
- entity
- tenant
- identifier
- version

Tenant information is included where isolation requires it.

## TTL

Caches can define a TTL and optional stale-while-revalidate interval.

```text
WRITE
 ↓
TTL
 ↓
FRESH
 ↓
EXPIRED
```

The reference layer models timing contracts rather than implementing a cache server.

## Invalidation

Invalidation can target:

```text
EXACT
PREFIX
TAG
```

Invalidation is explicit and can be tracked to completion.

## Consistency

Supported reference modes:

```text
EVENTUAL
READ_YOUR_WRITES
STRONG
```

A production cache adapter must map these semantics to actual storage/cache behavior.

## Read-through

On a miss:

```text
Cache
 ↓ MISS
Repository / Loader
 ↓
Populate Cache
 ↓
Return
```

## Write-through

Writes can update backing storage and cache as one logical operation:

```text
Write
 ↓
Backing Store
 ↓
Cache
```

The exact atomicity guarantees belong to the implementation adapter.

## Materialized views

Frequently consumed projections can be represented as materialized views with:

```text
EVENT
SCHEDULED
ON_DEMAND
```

refresh modes.

## Stampede protection

The reference contract supports:

```text
SINGLE_FLIGHT
REQUEST_COALESCING
JITTERED_TTL
```

These patterns reduce duplicate expensive loads during cache misses/expiry.

## Observability

Cache operations can emit:
- operation
- hit/miss
- latency
- cache
- key

This feeds M150 telemetry.

## Relationship

```text
M167 Persistence
      ↓
M168 Cache / Read Optimization
      ↓
M150 Telemetry
      ↓
M161 Workflows / M162 APIs
```

M164 configuration can control TTL and rollout policies.

M166 privacy constraints must still apply to cached data.

## Important boundary

The reference layer does not implement Redis, Memcached, distributed locking, a materialized-view database, cache replication or physical cache eviction.
