# M122 — Distributed Cache, Incremental Build & Dependency Invalidation

M122 makes repeated builds efficient by reusing valid work and rebuilding only affected dependency chains.

## Fingerprints

A node input can be converted into a deterministic content fingerprint.

```text
Input
  ↓
Canonical representation
  ↓
SHA-256 fingerprint
```

## Cache keys

A cache key can combine:
- node type
- input fingerprint
- configuration fingerprint
- policy version

This prevents incompatible outputs from being reused accidentally.

## Cache reuse

```text
Cache lookup
     ↓
Entry exists?
     ↓
Validate fingerprint/config/policy
     ↓
REUSE
```

A cache hit alone is not sufficient if the entry does not match the current build contract.

## Dependency invalidation

When a node changes, downstream dependents are recursively invalidated.

Example:

```text
Source
  ↓
Concept
  ↓
Scene
  ↓
Lesson
  ↓
Course
```

Changing Concept invalidates:

```text
Concept → Scene → Lesson → Course
```

but does not invalidate unrelated branches.

## Incremental build

The build planner can classify nodes as:
- REBUILD
- REUSE
- BUILD

This is the key mechanism for reducing repeated generation and rendering.

## Policy/configuration changes

Cache keys can include configuration and policy versions.

Therefore a change in a relevant generation policy can intentionally prevent reuse of stale artifacts.

The exact invalidation scope should be defined by the dependency graph.

## Metrics

Reference metrics include:
- cache hits
- cache misses
- rebuild count
- cache hit rate

These can feed M116 observability.

## Relationship

M120 provides immutable artifact identities.

M121 provides workflow execution.

M122 decides which work is reusable and which work must be recomputed.

## Important boundary

A cache is an optimization, not the source of truth.

The artifact store and provenance records remain authoritative.
