# M95 — Multi-Modal Renderer Orchestration & Backend Adapter Layer

M95 creates the boundary between educational/production semantics and rendering technology.

## Renderer-independent contracts

Upstream systems specify what must be produced.

They do not need to specify:
- Remotion
- SVG
- Canvas
- WebGPU
- Blender
- a particular audio engine
- a particular document renderer

Instead, the contract specifies a representation and its requirements.

## Backend registry

A backend declares:
- backend class
- capabilities
- versions
- resource profile

Examples of backend capability classes include:
- 2D vector
- 2D animation
- 3D
- video
- audio
- interactive
- simulation
- document
- GPU compute
- text

## Capability routing

The orchestrator filters backends based on whether they can satisfy the contract.

This prevents an incompatible renderer from being selected simply because it is available.

## Adapter layer

Each backend can expose a normalized adapter.

The adapter maps:
- common inputs → backend inputs
- backend outputs → common outputs
- backend errors → normalized errors

This isolates vendor/tool-specific APIs.

## Multi-backend execution

Different assets in the same lesson can use different backends.

For example:
- diagram → vector renderer
- animation → Remotion
- simulation → WebGPU
- narration → audio backend
- final composition → video backend

The semantic contract remains unchanged.

## Backend selection

Compatible backends can be ranked using replaceable signals such as:
- quality
- latency
- cost
- resource availability
- feature fit
- version compatibility

The reference implementation keeps the scoring mechanism intentionally simple so a future optimizer can replace it.

## Failure boundary

If no compatible backend exists, the system emits `NO_COMPATIBLE_BACKEND`.

It does not silently substitute an incompatible renderer.

## Relationship

M93 defines production contracts.

M94 schedules the production DAG.

M95 maps those contracts to actual rendering/execution backends.

M96 can build the Render Verification, Quality Assurance & Deterministic Validation Engine: inspect produced artifacts against contracts, provenance, timing, visual, audio, interaction and pedagogical constraints before accepting them into the build.
