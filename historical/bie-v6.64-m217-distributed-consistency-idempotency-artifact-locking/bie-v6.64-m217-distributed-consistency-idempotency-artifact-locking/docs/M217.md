# M217 — Distributed State Consistency, Idempotency, Exactly-Once Effects & Artifact Locking

M217 protects the distributed runtime introduced by M216 from duplicate and conflicting effects:

```text
Worker
  ↓
Idempotency Key
  ↓
Versioned State / CAS
  ↓
Artifact Lock + Lease
  ↓
Fencing Token
  ↓
Guarded Write
  ↓
Commit Record
  ↓
Reconciliation
```

## Idempotency

The same operation key and fingerprint returns the existing operation rather than creating a duplicate effect. A reused key with a different fingerprint is rejected.

## Versioned state

Compare-and-set prevents stale workers from overwriting newer state.

## Artifact locking

Only the current lock owner can write a protected artifact.

## Leases

Ownership can be represented as a time-bounded lease contract.

## Fencing

Monotonically increasing fencing tokens allow storage layers to reject stale workers even after a lease/lock changes owner.

## Reconciliation

Replicated state candidates can be compared by version and value to detect consistency or conflicts.

## Commit records

A commit links artifact, owner, idempotency key, fencing token and checksum into a traceable effect record.

## Exactly-once boundary

The architecture provides exactly-once *logical effects* through idempotency plus guarded commits; physical infrastructure may still retry delivery, but duplicate effects are suppressed.

## Boundary

M217 defines consistency contracts. Durable databases, distributed locks and object-store conditional writes are implementation choices for deployment.
